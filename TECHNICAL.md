# Kuji (Куджи) – Конструктор логических деревьев событий (FTA + ETA)

Десктопное приложение для автоматизированного построения **логических
деревьев событий** и расчета частот возникновения пожара по Методике
МЧС России от 26.06.2024 № 533 (Прил. № 1, 2) и ГОСТ 12.1.004-91
(прил. 3) с экспортом в **единый отчет DOCX по шаблону ГОСТ Р 21.101**
(встроенный pandoc).

## Парадигма (сессия 10)

Пять типов сценариев: **ТГМ** (твердые горючие материалы), **ГГ**
(горючие газы), **ГЖ** (горючие жидкости), **ЛВЖ**
(легковоспламеняющиеся жидкости), **Пыль**. Структура дерева
инвариантна – одна и та же для любого типа:

```
[Наличие вещества] ──┐
                     ├→ [Образование горючей среды (ГС)] ──┐
[Наличие окислителя]─┘                                    ├→ [Возникновение
                       [Появление источника зажигания] ───┘    пожара]
```

События на холст свободно НЕ размещаются: конкретные разновидности
причин выбираются в свойствах нод ГС/ИЗ из базы данных кнопкой
«Добавить причину» (разгерметизации П1.1, утечки трубопроводов П1.2,
отказы по табл. 9 прил. 3 ГОСТ 12.1.004-91, молния, статическое
электричество…). Для ГГ/ГЖ/ЛВЖ каждая разгерметизационная запись
развернута в **строки по диапазонам массового расхода истечения**
(табл. П2.1): «отверстие 5 мм» – три строки (< 1 / 1–50 / > 50 кг/с),
«полное разрушение» – своя строка «полный разрыв»; каждая строка –
**независимая причина**, порождающая сценарии только своего диапазона
(все режимы пожара диапазона появляются автоматически). Прямые события
П1.1, ТГМ-поверхность и пыль – одна строка без диапазона. Причины можно
перетаскивать друг под друга (зависимые ветви И-гейта:
Q = Q(родитель) × Q(потомок), цепи любой глубины – см. «Иерархия»).

Расчет (утвержден заказчиком):

```
Q_сценария  = Q_наличия вещества × Q_наличия окислителя
               × Q_разновидности ГС × Q_разновидности ИЗ × P_типа горения
Q_участок,k = Σ Q_сценариев × K_σ
```

* **ТГМ**: Q_ГС = a₁ × значение уровня (табл. П1.3) либо a·F^b
  (табл. П1.4, при значении > 10 000) – значение первого уровня с
  явной величиной (участок по типу м/м²/м³ → помещение → здание;
  наружная установка – своя);
* **ГГ/ГЖ/ЛВЖ/Пыль**: Q_ГС – частота разгерметизации (П1.1) либо
  удельная частота утечки × значение по типу места (П1.2); сессия 17
  (решение заказчика): причины П1.1/direct умножаются на значение
  СОБСТВЕННОГО типа владельца – F (м²) / L (м) / V (м³) из инспектора,
  скобка формулы показывает множитель явно: `(4·10⁻⁵·86)`; смена типа
  или значения участка пересчитывает формулы, ΣQ и статус-бар
  немедленно; не задано – множитель 1, скобка без множителя
  `(4·10⁻⁵)`; П1.2 и ТГМ П1.3/П1.4 не изменились (двойного умножения
  нет); зависимые ветви причин дают произведение множителей вдоль
  цепи (Q = Q(родитель) × Q(потомок));
* **P_типа горения** – табл. П2.1 по массовому расходу (<1 / 1–50 /
  >50 кг/с / полный разрыв) и среде (газ / двухфазная / жидкость):
  мгновенное → факельное горение (пролив для жидкости),
  последующее → пожар-вспышка (пролив), с избыточным давлением →
  сгорание (взрыв) топливовоздушной смеси; пыль – дефлаграция и
  детонация; «Огненный шар» – переключатель ноды (2,5·10⁻⁵ год⁻¹
  на аппарат);
* каждая развернутая строка выбора порождает сценарии СВОЕГО диапазона
  расхода (все режимы диапазона по среде – автоматически); строки без
  деления по расходу порождают все четыре диапазона, как раньше;
  физическую правдоподобность комбинаций подтверждает инженер во
  внешнем расчете.

## Иерархия объектов

Территория → Здание → [Пожарный отсек] → Помещение → **Участок**;
**Наружная установка** – самостоятельный аппарат под Территорией
(уровень Здания). Деревья создаются только на Участках и Наружных
установках – кнопкой **«Добавить дерево»** на панели иерархии (правее
«Добавить наружную установку», меню пяти типов; на помещении сначала
автоматически создается «Участок N»); тип Участка выбирается в свойствах:
«участок (м²)» – по умолчанию (причины: пожар по поверхности),
«линейный объект (м)», «аппарат/установка (м³)» (причины:
разгерметизации); пользователь может переименовать Участок в
«Аппарат 1», «Трубопровод 1» и т.п. Значение уровня по его типу
(площадь м² / длина м / объем м³) сразу входит в множитель ТГМ
(a₁ × значение; наружная установка – тот же селектор типа, проекты
до 6.5 открываются с типом «участок (м²)»). Под каждым владельцем в
иерархии – **строки его деревьев** (по типу сценария), детьми – все
добавленные причины: строки ГС с префиксом «Образование ГС:», строки
ИЗ – коротким названием; списки различимы с одного взгляда глифами
(сессия 16): ГС – янтарное **облако**, ИЗ – красное **пламя** (цвета
классов нод холста – одна семантика, один цвет); выделение строки
сценария показывает его
дерево, клик по строке причины открывает форму ноды ГС/ИЗ и
пунктирно выделяет ноду на холсте. **Перетаскивание причин**: зажать
ЛКМ на строке причины (под курсором – карточка с глифом строки и
названием: глиф 16 px + однострочный заголовок, усечение по пикселям,
рамка 1 px, четкость HiDPI) и бросить на причину того же списка
(ИЗ→ИЗ, ГС→ГС) – она становится зависимой ветвью И-гейта
(Q = Q(родитель) × Q(потомок); цепь дает одну строку с произведением
множителей, «Убрать» удаляет ветвь целиком с подтверждением).
**Отцепить зависимую причину** (вернуть на верхний уровень) можно
четырьмя способами (сессия 16): бросить на строку сценария, бросить
на строку владельца (участок/установка), ПКМ «Отцепить от родителя»,
бросить на пустое место или на крайнюю (верхнюю/нижнюю четверть)
зону строки причины своего списка; допустимые цели отцепления
подсвечиваются синим, у курсора появляется подсказка «Отцепить»;
порядок строк при этом не меняется. После дропа цель раскрыта,
перенесенная строка выделена. Объект перетаскивается под
допустимого родителя (поддерево целиком, по PARENT_RULES), строка
дерева – на другой участок/установка. Выделение помещения/здания показывает все деревья
дочерних участков. Контекстное меню объектов – только
«Переименовать…» и «Удалить с поддеревом…», строк причин –
«Отцепить от родителя» (для зависимых);
Delete удаляет строго ВЫБРАННОЕ (Ctrl/Shift-мультивыбор реальной мышью –
одно окно подтверждения на весь список; смена выделения не перестраивает
дерево); **выбранные строки причин** (в чистом выборе) Delete/мусоркой
удаляются КАК ПРИЧИНЫ с зависимыми ветвями – одно окно со списком
всех цепей, объект-владелец не затрагивается; строка сценария –
безопасный no-op (дерево удаляется выделением его ноды на холсте);
в смешанном выборе (причины + объекты) удаляются только объекты. Территория создается **только в корне** иерархии – независимо
от того, что выделено (вложенных территорий не бывает); файлы старых
версий с вложенными территориями чинятся автоматически при открытии
(территории поднимаются в корень со своими поддеревьями, недопустимые
размещения переносятся к ближайшему допустимому предку; уведомление в
строке состояния). Новые участки и наружные установки добавляются
**свернутыми** (здания/помещения/отсеки – раскрыты); свернутость
переживает клики и пересборки и **сохраняется в файле проекта**
(ui-словарь формата 5, восстанавливается при открытии).

## База данных (v6.2, редактируемые библиотеки и реестр источников – сессии 13–18)

Пять типов сценариев; **редактируемая библиотека «Горючие среды (ГС)»**
(«Наименование ГС | Частота, год⁻¹ | Примечание»: П1.1 – инженерный
формат «4,6·10⁻³ год⁻¹», П1.2 – «м⁻¹·год⁻¹ × L», ТГМ-поверхность –
a₁·F по табл. П1.3/П1.4); строки библиотеки **развернуты по
диапазонам массового расхода истечения** (правка названия/частоты
меняет запись целиком, удаление убирает запись со всеми строками);
**редактируемая библиотека «Источники зажигания (ИЗ)»** («Наименование
ИЗ | λ, год⁻¹ | Примечание»: «Удар молнии» – расчётная величина
N_у.м·(1 − η_МЗ), нагретые вещества – «P = 1 (вероятность)»);
**справочник «Таблица типовых режимов пожара»**
(только чтение: режим | базовая частота | примечание); таблицы П1.3 /
П1.4 / П2.1 – под-вкладками; **редактируемые шаблоны оборудования**
(«Шаблоны оборудования»: справа форма – доступна только после кнопки
**«Редактировать»** (кнопка превращается в «Сохранить» + «Отмена»;
отмена возвращает снимок записи, сохранение фиксирует правки):
название, категория, тип сценария, списки «Разновидности ГС» (включая
строки диапазонов расхода) и «Разновидности ИЗ»; кнопки
[Добавить]/[Удалить] внизу окна; новый шаблон – «Новый шаблон
оборудования», категория «Прочее», тип «gg», пустые списки (сразу в
режиме редактирования); удаление предупреждает количеством
использующих деревьев); **«Защитные средства» – редактируемая библиотека мер**
(«Наименование средства | Коэффициент | Носитель | Примечание»):
правка коэффициента существующей меры ВЛИЯЕТ на расчет (движок читает
запись базы), новая мера – переключатель с универсальным множителем k
на выбранном носителе (нода ГС/ИЗ, помещение, здание). Числа – всегда
инженерный формат с запятой («3,2·10⁻⁵»), без «3.2e-05». Кнопки
«Добавить запись»/«Удалить запись» – слева внизу окна; удаление
используемой записи предупреждает о числе деревьев. Все таблицы:
ширины столбцов по содержимому без сжатия, горизонтальный ползунок
при нехватке места, перенос строк ≤85 символов по словам (длинное
слово – по слогам с «–»; развороты списков – той же ширины, потолок
85 символов, кнопка закрытого списка свою ширину не меняет).
Примечания мер – по канону сессии 11:
«формула (пункт источника) – краткое описание». Окно БД: нижняя панель
«Сохранить»/«Закрыть» справа; правки сохраняются в
knowledge_base.json кнопкой «Сохранить».

**Реестр источников (сессия 18, БД v6.2)**: в базе появился раздел
`sources` – записи «источник» (нормативный документ с указанием
таблицы/пункта); у библиотек ГС/ИЗ/мер добавлена колонка «Источник»
(название из реестра; пусто – «–»; правка – двойным кликом, выбор из
списка + быстрое добавление). Старые файлы (схема 6.1) открываются
прозрачно: при загрузке строки `source` сворачиваются в реестр с
дедупликацией, поля записей перепривязываются на идентификаторы.
Вкладка **«Источники»**: таблица наименований, добавление/правка/удаление
(удаление занятого источника предупреждает количеством ссылающихся
записей и очищает привязки). Кнопка **«?»** слева от «Закрыть» открывает
справку по базе данных – включая мини-нотацию формул (индексы `F_зд`,
степени `10^-2`, макрос `\lambda`, инженерные числа и кареточный
ввод `3,2^-5`) – все примеры соответствуют реальному рендереру.

## Интерфейс

* границы трех панелей (иерархия | холст | инспектор) перетаскиваются
  мышью (QSplitter); состояние сплиттера и геометрия окна сохраняются
  НЕ только при закрытии, но и повороте разделителя (дебаунс ~300 мс) –
  пропорции переживают любой выход, включая завершение процесса;
  восстановление применяется повторно после первого показа (ловушка
  restoreState до layout); размер и положение главного окна, окна БД и
  pop-out «Документ» запоминаются между запусками (окна – и при любом
  скрытии; без авто-открытия);
* память файловых диалогов разделена (сессия 19, LOCKED): сохранение и
  открытие ПРОЕКТА – ключ `ui/last_dir`, экспорт ОТЧЕТА – СВОЙ ключ
  `export/last_dir` (исходники проектов и отчеты живут в разных папках;
  общий ключ уводил бы «Открыть проект» в папку отчетов). Цепочка
  фолбэков у обоих ключей одна: своя папка → папка проекта → Рабочий стол
  (каждая проверяется на существование). Экспорт пишет `export/last_dir`
  в ДВУХ случаях: успешная запись файла и выбор пути в «Обзор…» (даже
  если диалог затем отменен);
* **хранилище настроек – явный INI, а не реестр (сессия 19, п.3).**

**Открытие отчёта – через explorer.exe (сессия 19, раунды 2–3).** Заказчик
измерил дважды: предупреждение Word «в документе Normal.dotm обнаружено
содержимое, которое не удалось прочитать» появляется ТОЛЬКО при открытии из
программы, тот же файл из Проводника открывается штатно, а зачистка пакета
(раунд 1) предупреждение не сняла. Значит дело не в файле, а в способе
запуска: и `QDesktopServices.openUrl` (URL-форма пути), и `os.startfile`
порождают WINWORD.EXE как потомка нашего процесса, и Word наследует PATH с
каталогами встроенного Python и PySide6, рабочую папку проекта и
COM-контекст GUI-потока Qt. Проводник же запускает Word из своей среды.
Поэтому `MainWindow._open_path` идёт по цепочке:
(1) `_launch_via_explorer` – `subprocess.Popen([explorer.exe, path], cwd=папка
файла, env=очищенный PATH, close_fds=True, CREATE_NO_WINDOW)`, где из PATH
выброшены сегменты, содержащие `runtime`, `pyside`, `shiboken`, `qt`;
(2) `_launch_via_startfile` – `os.startfile(path, "open")`;
(3) `QDesktopServices.openUrl`. Оба первых шага – ШВЫ (тесты подменяют
методы класса и никогда не порождают реальные процессы), каждый шаг пишется
в `key_debug.log` строкой `open-report | …` через `latin_keys.debug_line()`.
Переменные окружения `APPDATA`, `LOCALAPPDATA`, `USERPROFILE` программа не
меняет ни в коде, ни в `run_app.cmd` (проверено) – Word ищет свой
`%APPDATA%\Microsoft\Templates\Normal.dotm` там же, где и всегда.

**Ход формирования отчёта (сессия 19, раунд 2).** `export_docx(...,
progress=None)` принимает извещатель `progress(value: float, message: str)`
с долей 0..1 и русской подписью этапа; этапы: «Подготовка документа» (0.02),
«Рисование схемы: <владелец>» (0.05…0.50, по числу владельцев), «Сборка
текста отчета» (0.55), «Конвертация в DOCX» (0.60), «Проверка и зачистка
файла» (0.88), «Проверка состава отчета» (0.95), «Готово» (1.0). Исключение
из приёмника глушится – индикатор не имеет права ломать экспорт;
`visual_qa_runner.py` вызывает `export_docx` без `progress` (прежний
контракт). Окно индикатора – `eta\ui\dialogs.py::ReportProgress`: НЕ
модальное (`show()`, не `exec()`), потому что экспорт идёт в GUI-потоке;
между этапами оно перерисовывается через `_pump()` (processEvents).
Создаётся через шов `DocxExportDialog._make_progress()` – тесты
подменяют его (None = экспорт вообще без второго окна) и никогда не
показывают модалок. Закрыто и при успехе, и при провале экспорта.

**ЛОВУШКА (проверено живьём, сессия 19):** pandoc нельзя ждать через
`Popen` + `poll()` в цикле, если stdout/stderr никто не читает – при полном
буфере трубы pandoc блокируется навсегда, и тестовый прогон висел минутами
вместо секунд. Поэтому ждём блокирующим `subprocess.run(..., timeout=300)`;
полоса в это время стоит на 60% с подписью «Конвертация в DOCX» (у pandoc
нет промежуточного прогресса). Если понадобится плавность, единственный
правильный путь – поток-читатель труб, а не пустой цикл ожидания.
**ЕЩЁ ОДНА:** в offscreen любое информационное окно – это вечное ожидание.
Например, `add_kind("area")` прямо под зданием (без помещения) показывает
окно недопустимой вставки, и прогон замирает без ошибок: иерархию в тестах
строить только по допустимой цепочке «территория → здание → помещение →
участок».

**Формулы как настоящий математический OOXML (сессия 19, п.4, LOCKED).**
Отчёт больше не печатает формулы текстом с юникод-надстрочниками. Markdown
для pandoc содержит LaTeX-математику: `$$ … $$` (выключная, своим
абзацем) и `$ … $` (строчная, в тексте и ячейках таблиц), из которых
pandoc собирает `<m:oMathPara><m:oMath>…` и `<m:oMath>` – нативные
объекты Word (редактируются двойным щелчком, выравниваются по знакам).
Измерено в `qa_report.docx`: 120 `m:oMathPara`, 324 `m:oMath`, и НОЛЬ
текстовых прогонов с `⁻`/`²`/`³` – то есть перевод покрыл все числа,
размерности и формулы отчёта. Выключные формулы pandoc помечает
`<m:jc m:val="center" />`, что и есть требуемое «по центру».

* переводчик – чистый модуль `eta\export\math_omml.py` (`expr`, `inline`,
  `display`, `has_math`): надстрочники/подстрочники, `_{\text{…}}` для
  кириллических индексов, `\text{…}^{…}` для единиц, `\cdot`/`\times`/
  `\sum`/`\exp`/греческие, запятая мантиссы как `{,}`. ЭКРАН И МАТРИЦА В
  ИНТЕРФЕЙСЕ не изменились – инженер по-прежнему читает «9·10⁻⁵»; LaTeX
  рождается только при сборке .docx;
* ГРАНИЦА: в `$…$` уходит то, что является числом, величиной, размером или
  формулой (значения параметров, колонки «Величина» и «Формула», ячейки
  матрицы, строки «Результаты расчета», заголовок колонки `Q, год⁻¹`).
  Русская проза (названия сценариев, подписей, источников) остаётся
  ТЕКСТОМ и печатается отдельным абзацем после выключной формулы –
  смешивать длинный русский текст с математикой в одном абзаце нельзя;
* каждый фрагмент упаковывается РОВНО ОДИН раз: готовые куски пряться в
  guard-маркеры `\x00N\x00`, потому что вложенный `\text{\text{…}}` texmath
  НЕ парсит и pandoc тихо отдаёт `$…$` как текст (проверено пробой);
* `_md_escape` обязан беречь формулы: регулярка `_MATH_SPAN` захватывает
  `$…$`/`$$…$$` ГРУППОЙ, иначе `re.split` выбрасывает математику из строк
  вместе с экранированием (именно так на первом прогоне пропали формулы в
  таблицах – 181 `m:oMath` вместо 324).

**Зачистка пакета перед выдачей (сессия 19, п.2).** `eta\export\docx_tidy.py`
(`tidy_package`) вызывается в `export_docx` СРАЗУ после pandoc и перед
валидацией. Она (1) убирает из `*.rels` связи, на которые ссылаться не
должно (`extended-properties`, `custom-properties`, `thumbnail`), и
НЕИСПОЛЬЗУЕМЫЕ медиа/гиперссылки; (2) строит достижимость от
`_rels/.rels` и выбрасывает сирот вместе с их `Override` в
`[Content_Types].xml`; (3) вычищает из `word/settings.xml`
`attachedTemplate`, `linkStyles`, `savePreviewPicture`, `rsids`; (4)
проверяет, что каждый XML читается и ни одна внутренняя связь не ведёт в
никуда, и атомарно заменяет файл. Смысл: ГОСТ-шаблон клонирован из рабочего
документа, и в отчёт приезжали `docProps/app.xml` с
`<Template>Normal.dotm</Template>` (из-за упоминания Normal.dotm Word
запускал восстановление и на «Да» ПЕРЕЗАПИСЫВАЛ пользовательский

ДВЕ ЛОВУШКИ зачистки, проверенные пробой: (а) связи `styles`, `settings`,
`numbering`, `theme`, `fontTable`, `webSettings`, `footnotes`, `comments`,
`header`, `footer` НЕЯВНЫЕ – в `document.xml` на них нет `r:id`, поэтому

обвязки (колонтитулы!) считается недостижимым.

**Ловушки автоматизации (сессия 19).** `DocxExportDialog` импортируется
ВНУТРИ `MainWindow._export_docx`, поэтому тесты подменяют атрибут модуля
`eta.ui.dialogs`, а не `eta.ui.main_window`. Вся цепочка «экспорт →
память папки → вопрос → открытие» вызывается методом
`MainWindow._after_docx_export(path)` – ее тесты и гоняют напрямую, без
`exec()` (модальный диалог в offscreen вешает прогон; Ctrl+E там не
отправляют никогда). Холст показывает ВСЕ деревья проекта, только когда в
иерархии ничего не выбрано (`_current_trees()`), – тест «два дерева двух
владельцев» обязан снять выделение и сбросить `_selected_scenario`.
Точку двойного клика всегда проверяют по `canvas.itemAt(...)`: экран
offscreen 800×800, центр ноды может уйти за вьюпорт.
**Правило контура QA (сессия 19):** содержимое .docx читают ВНУТРИ
`with zipfile.ZipFile(...) as z:` – словари проверок строятся уже СНАРУЖИ
блока, и любое `z.read()` там падает «Attempt to use ZIP archive that was
already closed» (ловил реально: список частей и «нормальный» слепок XML
надо сохранять в переменные внутри `with`). Тесты `app_settings` не должны
вызывать `migrate_from_registry()` – он читает НАСТОЯЩИЙ реестр; в тестах
подменяют `registry_settings()` на герметичный источник.

Зависимостей вне встроенного окружения нет (DOCX-экспорт использует
встроенный `runtime\pandoc\pandoc.exe`; PDF-конвертация для визуальной
приемки – опциональный ручной `run_qa_pdf.cmd`, сам отказывается
работать при открытом пользователем Word).
